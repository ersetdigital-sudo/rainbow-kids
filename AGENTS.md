# Base44 sandbox notes

- **Run:** `docker compose -f docker-compose.base44.yml up -d --build`. One service (`web`), `node:22`, repo bind-mounted at `/app`, `npm ci` then `next dev` on `0.0.0.0:3000`. `node_modules` lives in the named volume `base44_node_modules`, so dependency changes need `docker compose -f docker-compose.base44.yml restart web` (it reinstalls) — do not delete volumes.
- **No backend, no database.** All data is client-side `localStorage` (`rk_data_v3`, see `src/lib/persist.ts`).
- **No store data in code.** `emptyDb()` + `DEFAULT_PERMS` live in `src/lib/workspace.ts`; there is no demo/seed dataset any more (the old "Muat data contoh" button is gone). "Kosongkan semua data" in Pengaturan Toko wipes products, customers, transactions and users. The legacy key `rk_mock_v2` is removed on load so old demo snapshots never reappear.
- **Supabase (optional, for real use).** Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`; they arrive through `env_file: /run/base44/app.env` in `docker-compose.base44.yml` (never put them under compose `environment:`). When they are present: a full-screen login overlay gates the app (`src/components/auth/LoginScreen.tsx`), the store is split across one table per domain (`supabase/schema.sql` — must be run once in the Supabase SQL editor), and users are real Supabase Auth accounts with email + password. Data access lives in `src/lib/db/` — one module per domain (`products`, `partners`, `sales`, `purchases`, `opnames`, `approvals`, `settings`, `logs`) plus `client.ts` (query helpers + row diff). `db/index.ts` exposes `loadStore()`/`saveStore()`; `remote.ts` debounces saves and writes only the rows that changed against the last synced snapshot, so a new field needs a column + mapper, not a store rewrite. Nested proposal payloads (saleRequest, revision, customerChanges, …) stay in the `approvals.detail` jsonb column; array order is preserved by the `position` column; child tables (`product_variants`, `sale_items`, `sale_payments`, `purchase_items`, `opname_lines`) use `on delete cascade` from their parent. While the project has zero auth users, the login screen shows "Buat akun Owner" (`POST /api/bootstrap`); afterwards accounts are created from Pengaturan → Pengguna via `POST /api/users` (service role, caller session required).
- **Login:** `signIn(email, password)` in `src/lib/auth.tsx` is the only entry point — it trims/lowercases the email, validates email + password locally, calls `supabase.auth.signInWithPassword`, and maps Supabase Auth errors to Indonesian messages (`Invalid login credentials` → "Email atau password salah"). `LoginScreen` renders the result and clears the password field on failure; the session is picked up by `onAuthStateChange`, which opens the gate. Verified end to end against the real Supabase project with a temporary account (deleted afterwards).
- **Local mode without credentials.** If the Supabase vars are absent the app runs exactly as before: no login, data only in this browser's `localStorage`, no network calls.
- **Users come from Supabase Auth**, never from code: `db.users` is replaced after login by `GET /api/users` (service role, caller token required), which lists real accounts — role from `user_metadata.role`, `active: false` when the account is banned. Role/name/email/status edits go through `PATCH /api/users` first (`src/lib/users.ts` → `patchAccount`), so Supabase Auth is the source of truth; `inviteUser` creates the account via `POST /api/users`. In local mode (no Supabase env) the same actions only touch the browser snapshot. The first account is Owner and becomes the active-user marker (`db.user`).
- **Schema check:** `GET /api/bootstrap` also returns `tableReady` (probes `store_settings`); when `supabase/schema.sql` has not been run, the login screen shows a warning and every failed read/write reports a toast instead of failing silently. While the tables are missing nothing persists to Supabase (localStorage only). `db.users`/`db.user` are never written to a table: the list comes from Supabase Auth and the active-user marker stays per browser. One-time migration from the old single-row schema: `db/index.ts#readLegacyState` imports a non-empty `app_state` row into the new tables on first load, so `supabase/schema.sql` can be switched over without losing data.
- **Hydration vs localStorage:** SSR renders the empty workspace, so the saved browser snapshot must not be used during hydration. `getSnapshot()` keeps returning the server snapshot until `activateBrowserSnapshot()` runs (a `setTimeout(0)` after mount in `StoreProvider`). Using `localStorage` earlier causes "Hydration failed" on the sidebar brand (`src/components/layout/Sidebar.tsx`).
- **No external credentials.** The only env var is optional `NEXT_PUBLIC_SITE_URL` (canonical URL / `sitemap.xml` / `robots.txt`); it falls back to `https://rainbowkids.id`.
- **Preview origin:** `next.config.ts` appends `3000-$BASE44_PUBLIC_HOST_SUFFIX` to `allowedDevOrigins` only when `BASE44_PREVIEW_MODE === "1"`, so the proxy origin can fetch dev assets/HMR. Unset/other values keep the original config.
- **Verify:** `curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/` returns 200, and the container logs show live Turbopack compilation (dev source, not a prebuilt bundle).
- **Lint:** `docker compose -f docker-compose.base44.yml exec -T web npm run lint`.
- **Stale CSS cache:** the repo ships a `.next` cache from import time. If rules from newer parts of `src/app/globals.css` silently never load (e.g. the bell panel `.act-*` opens unstyled and lands at the end of the document), it is not a code bug: stop `web`, `rm -rf .next`, then `up -d web` to force a clean Tailwind/Turbopack compile.
